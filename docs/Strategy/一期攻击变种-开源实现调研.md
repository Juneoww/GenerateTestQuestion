# 一期攻击变种：开源实现调研

日期：2026-11-13
状态：调研结论与待验证建议；2026-11-16 已按用户确认的开源复用边界更新。**尚未引入、移植或执行第三方代码**。

## 1. 问题和结论

目标是对现有三类题集中的原子问题生成单条静态变种，不调用攻击模型、不运行被测系统，并兼容现有 Python 桌面程序及 Windows EXE。

业界已有大量对应实现，**不需要从零发明编码或规则算法**。其中 Promptfoo 的静态策略与截图中的名称尤其接近；微软 PyRIT 也有可调用的 Python 转换器；NVIDIA garak 提供编码探针和提示包装。

用户已明确：**不部署或运行完整 Promptfoo 项目**，只将本功能必需的代码或数据按许可证要求提取、移植进当前 Python 项目。其他候选项目也遵循按需最小复用原则；不为单项策略整体引入完整扫描框架。建议先做一个**固定版本、可重复的兼容性验证**，再决定逐项采用方式：

1. 对 Base64、hex、URL、ROT13 等标准编码，直接使用 Python 标准库已有实现；这也是复用现成开源代码，不需要自行实现算法。
2. 对同形字、Leetspeak、Morse、Pig Latin、camelCase 等，优先比较 Promptfoo、PyRIT 等固定版本的具体函数或映射；在许可证允许的前提下只提取或移植所需代码和数据，保留版权与来源，并用上游样例验证行为。TypeScript 函数需要翻译为 Python，不能当作可直接导入的 Python 模块。**究竟哪段适合抽取，需先验证。**
3. 对指令包装，优先考察开源静态模板集是否符合本项目的输入面、语言和断言；不足的内容用项目自己的本地模板补齐。不要把动态攻击或远程生成误当成静态模板。
4. 本项目仍需自己的适配层：把现有原题传给策略、限制适用范围、记录原题与变种、处理错误并导出 Excel／图片；这些不是引入第三方转换器就自动具备的功能。

## 3. 基础规则：逐项候选

表中的来源表明存在相应实现，**不代表已在本项目中调用或保证输出完全一致**。Promptfoo 来源可先以 [0.125.1 的编码源码](https://github.com/promptfoo/promptfoo/blob/0.125.1/src/redteam/strategies/otherEncodings.ts) 为可复现对照；PyRIT 优先参考 [1.1.0 固定版本转换器文档](https://microsoft.github.io/PyRIT/1.1.0/api/pyrit-converter/)，使用前必须确认所选发行版 API 与行为。

| 本期策略 | 已有来源／实现 | 对本项目的建议与差异 |
|---|---|---|
| R00 basic | Promptfoo 有 basic；本项目已产生原题 | 直接保留现有原题，不生成重复记录。 |
| R01 Base64 | Python `base64`；PyRIT `Base64Converter`；[Promptfoo Base64](https://github.com/promptfoo/promptfoo/blob/0.125.1/src/redteam/strategies/base64.ts) | 优先标准库 UTF-8 编码；解码提示包装是单独选择，不能把纯编码与带包装视为完全相同。 |
| R02 ROT13 | Python `codecs`；PyRIT `ROT13Converter`；Promptfoo | 标准库可直接使用；中文通常不变，需检查保护字段并跳过无变化。 |
| R03 Leetspeak | PyRIT `LeetspeakConverter`；[Promptfoo 策略](https://www.promptfoo.dev/docs/red-team/strategies/leetspeak/) | 优先对比现成映射和确定性选项，锁定版本／映射；是否修改技术标识由适配层处理。 |
| R04 hex | Python `bytes.hex`；PyRIT 有 `BinAsciiConverter`；[Promptfoo hex](https://www.promptfoo.dev/docs/red-team/strategies/hex/) | 优先标准库对整题 UTF-8 编码；PyRIT 的词级转换未证明与整题字节输出一致。 |
| R05 homoglyph | PyRIT `UnicodeConfusableConverter`；[Promptfoo homoglyph](https://www.promptfoo.dev/docs/red-team/strategies/homoglyph/) | 验证固定替换表、随机性和中文效果；不得把相似字符扰动称为语义等价。 |
| R06 camelcase | [Promptfoo `toCamelCase`](https://github.com/promptfoo/promptfoo/blob/0.125.1/src/redteam/strategies/otherEncodings.ts) | TypeScript 可作为复用或移植候选；上游按空白分词，需验证中文、标点和受保护标识，不默认符合当前局部英文方案。 |
| R07 morse | PyRIT `MorseConverter`；Promptfoo `toMorseCode`；[garak 编码源码](https://github.com/NVIDIA/garak/blob/main/garak/probes/encoding.py) | **三者对不支持字符的处理不同**：PyRIT 文档写错误序列，Promptfoo 保留原字符，所查 garak 代码可能丢弃未收录字符。必须在转换前校验，明确跳过或保留，禁止静默丢失中文。 |
| R08 piglatin | Promptfoo `toPigLatin` | 优先研究上游词分割和大小写逻辑并做兼容样例；主要处理英文，中文本身不会自动变换。 |
| R09 emoji | Promptfoo `toEmojiEncoding`：UTF-8 字节映射为不可见变体选择符并附着在表情后 | 用户已确认一期采用此方式；复用前核对固定版本、许可证、字节往返和复制／Excel 保真。可见词语替换暂缓。见第 5 节。 |
| R10 URL 百分号编码 | Python `urllib.parse.quote_from_bytes`；PyRIT `UrlConverter` | 优先标准库，明确保留字符和 UTF-8；PyRIT 的默认参数可能与设计的全字节编码不一致。 |
| R11 二进制／八进制／十进制 | PyRIT `BinaryConverter`；Python 字节与整数格式化 | 上游 Binary 默认按字符位宽处理，现设计按 UTF-8 **逐字节**处理，不得直接视为同一输出；八进制、十进制可直接使用标准格式化能力。 |
| R12 HTML 实体／Unicode 转义 | Python `html`／`json`／字符串编码能力；PyRIT 有 `JsonStringConverter` | 明确逐码点 HTML 实体与 JSON `\\u` 转义协议、非 BMP 和解码往返；普通 HTML 转义不会自动把所有字符变成实体，需要适配。 |
| R15 大小写 | Python 字符串方法；PyRIT 有随机大小写转换 | 标准库直接处理最直接；固定大写／小写与随机大小写不是同一策略，需明确 ASCII／Unicode 范围。 |
| R16 空格、标点、分隔符 | PyRIT `StringJoinConverter` | 候选直接调用或抽取适配；按词转换与全句转换的标点、中文和保护字段行为需对照，不静默改变原意。 |
| R18 倒序 | PyRIT `FlipConverter`；Python 序列操作 | 需定义按码点还是按字素簇；对组合字符、表情、受保护标识要跳过或采用已验证的字素处理，不能仅凭名称认定安全。 |

R13、R14、R17、R19–R25 中用户明确暂缓的项目仍为后续小版本范围；R09 的 Promptfoo emoji 不可见字符编码是用户确认的独立一期例外，其他不可见字符规则仍暂缓。

## 4. 直接指令与结构边界：逐项候选

[Promptfoo 的静态 `jailbreak-templates` 文档](https://www.promptfoo.dev/docs/red-team/strategies/jailbreak-templates/)描述了现成模板，但其官方文档明确指出，模板集不覆盖所有特殊角色标记、结构化数据或分隔符场景。因此**不能把一个模板集等同于 I01–I09 全覆盖**。模板有版本和来源差异，也需审查是否会改变现有原题的目标、语言或断言。

| 策略 | 开源候选／实现建议 | 检查重点 |
|---|---|---|
| I01 直接覆盖 | Promptfoo 静态模板、PromptInject 的模块化模板候选；必要时项目内置固定模板 | 确保原题完整可追溯，模板只添加普通文本。 |
| I02 权威身份伪装 | Promptfoo 静态角色／开发者模式模板候选；筛选适用模板 | 声称的身份不是真实权限，检查是否扭曲原题目标。 |
| I03 角色／结构标签伪装 | PromptInject 或其他明确许可的模板候选；不足时项目自带固定标签模板 | 不创建真正的 system/developer 消息；上游模板是否覆盖具体标签须逐个确认。 |
| I04 拒绝抑制／格式约束 | 开源静态模板候选；项目可维护确定版本的中英固定模板 | 检查是否与原断言、格式要求冲突；标记待人工复核。 |
| I05 回答前缀 | 以开源模板示例或项目固定模板处理 | 不预先填入原题所要求的答案。 |
| I06 虚构授权规则 | 开源角色／授权包装候选；必要时本地固定模板 | 不声称获得真实授权，不修改权限。 |
| I07 JSON／XML／Markdown 包装 | Python 标准库序列化或受控模板 | 解析后原题必须一致；上游越狱模板集不等于结构化注入完整实现。 |
| I08 文本边界标记 | 明确授权的现成模板候选或项目固定文本 | 字符串标记不能改变 API 消息边界，也不代表真实截断。 |
| I09 隐藏上下文提取 | 搜索现有固定模板，但只适配原题已明确以同一目标为目的的记录 | 它是目标而非通用变换；不能对任意原题无条件增加新目标。 |

现阶段没有逐条验证上述开源模板与本项目 I01–I09 一一对应，也未决定复制具体模板；“候选”不等于现成可直接集成。

## 5. 必须先解决的行为差异

### 5.1 `emoji` 与其他暂缓的不可见字符

此前一期设计曾将 `emoji` 写为可见词语替换，如将“猫”替换成猫表情；这并不等于 Promptfoo 0.125.1 的 `emoji`。Promptfoo 的 `toEmojiEncoding` 是将文本的 UTF-8 字节映射成**不可见 Unicode 变体选择符**，附着在表情符号之后；上游[源码](https://github.com/promptfoo/promptfoo/blob/0.125.1/src/redteam/strategies/otherEncodings.ts)和[文档](https://www.promptfoo.dev/docs/red-team/strategies/other-encodings/)均说明这一点。

用户最新确认：**一期采用 Promptfoo 的不可见字符方式**，原设计中的可见词语→表情替换暂缓。R09 是对 R19 暂缓规则的具体例外，不代表引入其他不可见字符策略。该方式不需要词典；仍须确认第三方源码许可、仅提取必要逻辑并测试 Excel、剪贴板及 Unicode 往返。普通文字图片无法承载隐藏码点，不能把仅显示表情的图片当作完整变种，详见一期设计文档。

### 5.2 编码与原题包装

Promptfoo 的编码源码对测试变量执行转换；之前文档建议额外添加“解码并处理”的提示，两者输入不完全一致。[PyRIT 的 AskToDecodeConverter](https://microsoft.github.io/PyRIT/latest/api/pyrit-converter/#pyrit.converter.AskToDecodeConverter) 是单独的包装步骤。是否提供“仅编码”和“编码＋解码说明”应作为显式选择，不能把包装当作无差别实现细节；两者可能导致不同的测试结果。

### 5.3 中文与文本完整性

Base64、hex、URL 等可先转 UTF-8 字节；ROT13、Morse、Pig Latin、camelCase 通常主要作用于英文。各上游对不支持字符是保留、替换还是丢弃并不一致，必须按固定规则测试并明示。原题、工具名、占位符、身份及断言要保留可追溯信息，变种不能自动宣称与原题语义相同。

## 6. 用户确认的代码复用方式

| 方式 | 收益 | 需要验证的成本 |
|---|---|---|
| A. 直接依赖完整 PyRIT，在本地调用转换器 | Python 集成，复用上游实现和升级 | 非本期方案：为少量变种引入完整框架与用户的按需最小复用要求不符 |
| B. 随程序集成 Promptfoo／Node 运行时 | 更贴近截图中同名策略 | **明确不采用**：用户不希望部署完整 Promptfoo 或依赖其运行 |
| C. 标准库＋从已核实许可的上游提取／移植最小必需代码 | 直接复用现成标准算法及上游经过许可的具体实现，保持 Python 单程序 | **首选方案**：记录来源项目、版本／提交、文件、许可证与改动；仅引入必要的代码和数据，配备上游对照测试，并维护更新 |

**后续验证以方案 C 为准。** Promptfoo 0.125.1 的 `toMorseCode`、`toPigLatin`、`toCamelCase` 是其 TypeScript 文件中的字符串转换函数，但文件还引用项目自己的类型和映射辅助逻辑，因此不能直接原样导入 Python。应逐项抽取必要算法和许可允许的映射、翻译为 Python，并在适配层显式处理中文、受保护字段和跳过规则；标准编码直接调用 Python 标准库。方案描述并不代表已经提取代码、验证兼容性或确认每项都有可复用上游实现。
